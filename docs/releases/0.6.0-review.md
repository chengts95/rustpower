# RustPower 0.6.0 release review guide

This guide is an ordered review path for the experimental N-1 and CUDA/cuDSS functionality in RustPower 0.6.0. It separates user-facing behavior from implementation details and records the final CI evidence. It is a review checklist, not a request to publish a tag, GitHub Release, or PyPI upload.

## 1. Release scope and compatibility

Read the [release notes](0.6.0.md) first, then check these boundaries:

- Existing CPU power-flow APIs and default Cargo features remain unchanged.
- `experimental_n1` enables the fixed-partition N-1 API and its dynamic-KLU dependency for native Rust development.
- Python wheels use statically linked KLU. The separate `klu_dyn` CI job tests the dynamic backend; it does not describe wheel packaging.
- `experimental_n1_cuda` is opt-in for native builds. Ordinary Cargo builds neither compile nor load CUDA.
- CUDA and hybrid execution are experimental, Windows x64 only, limited to device 0, and currently require `initialization="base-ac"`.
- Prepare N-1 grids with `qlim=False`: contingency scenarios retain a fixed PQ/PV/Slack partition.

Detailed behavior and result semantics are in the [N-1 usage guide](../N1_USAGE.md). CUDA installation and fallback rules are in the [CUDA N-1 guide](../n1_cuda.md).

## 2. Python user path

### Installation

```bash
pip install rustpower
```

On Windows, install the optional NVIDIA runtime only when GPU execution is wanted:

```bash
pip install "rustpower[cuda]"
```

A normal installation and `import rustpower` do not require an NVIDIA driver or runtime. Linux and macOS wheels currently expose the CPU N-1 backend only.

### Minimal N-1 workflow

```python
import pandapower.networks as networks
import rustpower as rp

net = networks.case118()
grid = rp.PowerGrid.from_pandapower(net, qlim=False)
study = grid.prepare_n1(
    voltage_limits=True,
    line_loading_limit=100.0,
)

# auto uses CUDA only when the complete runtime/device probe succeeds.
report = study.run(workers=4, batch_size=8, backend="auto")
print(report.summary)
print(report.summary["backend"])

# Retry only numerical failures with a fresh DC start per scenario.
retry = study.run(
    report.numerical_failures,
    initialization="dc",
    workers=4,
    backend="cpu",
)

# Inspect rejected scenarios with every configured detail payload.
details = study.details(report.rejected_faults, workers=4, backend="cpu")
```

Review the following behavior against the [Python quick start and API sections](../N1_USAGE.md#python-bindings):

1. `study` owns an immutable prepared snapshot; subsequent source-grid edits do not change it.
2. Default status runs retain rejected numerical events, not every passing event.
3. Numerical failures, rejected faults, and island faults are separate selections.
4. Detailed reports expose event, watch-hit, and branch-flow columns with explicit row links.
5. Explicit `backend="cuda"` or `"hybrid"` raises an error when CUDA is unavailable; only `auto` falls back to CPU.

The executable regression example is [`scripts/test_n1_api.py`](../../scripts/test_n1_api.py). It covers ownership, sparse outputs, DC retry, CPU fallback, CUDA/hybrid equivalence, and GIL release.

```bash
RUSTPOWER_N1_DISABLE_CUDA=1 python scripts/test_n1_api.py
# On a configured Windows CUDA machine, omit the variable to include GPU tests.
python scripts/test_n1_api.py
```

## 3. Rust user path

The two complete examples are [`n1_run`](../../examples/n1_run.rs) and [`n1_retry_dc`](../../examples/n1_retry_dc.rs). Their shared case-loading and watch setup is in [`examples/common/n1.rs`](../../examples/common/n1.rs).

```bash
# CASE may be 39, 9241, or a pandapower CSV ZIP path.
CASE=cases/IEEE118/data.zip

# Status-only screening with bounded worker/result queues.
cargo run --release --features experimental_n1 --example n1_run -- \
  "$CASE" 4 8 status n1-events.json base-ac

# Detailed statuses and configured rule hits.
cargo run --release --features experimental_n1 --example n1_run -- \
  "$CASE" 4 8 details n1-details.json base-ac

# Retry NumericalFailure records from the status file with per-case DCPF.
cargo run --release --features experimental_n1 --example n1_retry_dc -- \
  "$CASE" n1-events.json n1-retry.json 4 30
```

`n1_run` demonstrates streaming collection into JSON without retaining all results. `n1_retry_dc` validates recorded device identities and rejects selections that belong to the topology-island path. An input with no numerical failures is reported explicitly rather than treated as a successful retry.

For a basic non-N-1 ECS power-flow entry point, use `cargo run --example ecs_net`; its source is [`examples/ecs_net.rs`](../../examples/ecs_net.rs).

## 4. CUDA backend review

Follow the [CUDA N-1 guide](../n1_cuda.md) in this order:

1. Installation and optional NVIDIA pip runtime packages.
2. `auto`, `cpu`, `cuda`, and `hybrid` backend selection.
3. The actual backend reported in `summary["backend"]`.
4. Runtime probing and `RUSTPOWER_N1_DISABLE_CUDA=1` deployment control.
5. Native build variables and embedded PTX compatibility.
6. Current model, platform, and device limitations.

The hybrid scheduler fills a bounded CUDA queue first and overflows work to CPU workers. This preserves result semantics but is not a universal performance guarantee. Review performance claims separately from correctness; the GPU benchmark reports are workload- and hardware-specific.

## 5. Source reading order

Read one layer at a time rather than following every call across the whole tree:

| Order | Source | Review focus |
| ---: | --- | --- |
| 1 | [`src/python/n1.rs`](../../src/python/n1.rs) | Python fault selections, snapshot ownership, backend arguments, NumPy report columns |
| 2 | [`src/n1/study.rs`](../../src/n1/study.rs) | High-level study API, Entity resolution, selections, retries, aggregate results |
| 3 | [`src/n1/execution.rs`](../../src/n1/execution.rs) | Producer/worker/collector flow, bounded queues, private workers, batching |
| 4 | [`src/n1/solver.rs`](../../src/n1/solver.rs) and [`numeric.rs`](../../src/n1/numeric.rs) | Newton solves, shared symbolic analysis, private numerical state, refactor/solve recovery |
| 5 | [`src/n1/outage.rs`](../../src/n1/outage.rs) and [`topology.rs`](../../src/n1/topology.rs) | Absolute CSC-slot patches, bridge pre-screening, slackless-island handling |
| 6 | [`src/n1/postprocess.rs`](../../src/n1/postprocess.rs) and [`watch.rs`](../../src/n1/watch.rs) | Branch flows, voltage/current rules, hit counts, detailed result association |
| 7 | [`src/n1/cuda.rs`](../../src/n1/cuda.rs) | Dynamic loading, preflight, backend selection, CPU fallback, hybrid dispatch |
| 8 | [`native/acpf_cuda`](../../native/acpf_cuda/) | C ABI boundary, managed buffers, FP64 Newton kernels, cuDSS calls, branch postprocessing |

The [parallel execution design](../design/n1_parallel_execution.md) explains why the queue and ownership structure is shaped this way. Keep the earlier low-level [`runner.rs`](../../src/n1/runner.rs) API distinct from the high-level study path.

## 6. Checks before release

Compile the two Rust examples without running a full GPU benchmark:

```bash
cargo check --features experimental_n1 --example n1_run --example n1_retry_dc
```

Run focused CPU N-1 tests when numerical behavior changes:

```bash
cargo test --features experimental_n1 --lib n1::
cargo test --features experimental_n1 --test n1_study --test n1_execution \
  --test n1_outage_patches --test n1_postprocess --test n1_watch \
  --test n1_topology --test klu_cache_reuse
```

Final public CI evidence:

- [Python Wheels run 42405817446](https://github.com/chengts95/rustpower/actions/runs/42405817446) passed for Linux x86_64, macOS arm64, and Windows x86_64.
- [Rust CI run 42405817480](https://github.com/chengts95/rustpower/actions/runs/42405817480) passed.
- These runs executed before the `paper` history cleanup at feature revision `085f96d8576fc3ac3a244a56cc2fe670dc185122` and CI integration revision `325198a23a5844f5d3effe5a5c3d96355f75fdf2`.

## 7. Artifact handoff

The release notes contain the complete [CI artifact inventory](0.6.0.md#ci-artifact-inventory). During this review, anonymous downloads of all three artifact ZIPs returned HTTP 401. No CI wheel has therefore been represented as downloaded or locally verified.

Before publication:

1. Download the three artifacts from the successful run using an authenticated GitHub session.
2. Verify each artifact ZIP against the recorded SHA-256.
3. Extract the wheels and record their exact filenames, sizes, tags, and individual SHA-256 values.
4. Check that the Windows wheel contains `acpf_cuda.dll` and its PTX compatibility artifact, but not the heavyweight NVIDIA runtime libraries.
5. Test installation in clean environments, including CPU-only import and N-1 execution without CUDA installed.

Only after those steps should the artifacts be attached to a release or uploaded to a package index.
