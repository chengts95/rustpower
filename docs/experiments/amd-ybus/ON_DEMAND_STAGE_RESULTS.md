# 按需枚举 J 邻居的 AMD：本阶段实际结果

【本次实际改动】
把新实验内核读取初始邻接的两个位置改成从 Ybus 生成编号；已有动态列表直接读取已写入的连续存储。原始参考、已认可的预合并路径、数值 J 组装和 KLU 路径均保留。

【实际执行路径】
对照：Ybus 分析 → 全部标量邻居编号写入完整表 → 原标量 AMD → 排列和逆排列。
新路径：Ybus 分析 → 每变量的长度/位置范围 → AMD 处理该变量时枚举初始邻居 → 筛选并写入动态结果 → 原标量决策与后序处理 → 排列和逆排列。

【是否完整展开初始 J 邻接】
排序开始前：否。运行中补建整张初始表：否。数值 J：照常保留。
9241 对照预存112376个初始邻居编号，新路径预存0个；这个0是代码路径审查结论，不是靠硬编码计数器单独证明。新路径入口只生成17037个边界和17036个长度/位置元数据，不生成邻居编号。初始列表读取仅由 InitialList::at 根据只读 Ybus 生成结果，不缓存这些结果。唯一的数值条目写入口 NeighborStorage::write 由消元构造/筛选调用。
诊断执行中：112376次初始邻居生成；17036个变量实际读取；234906次动态写入，82188个不同位置实际被写入。没有回退成完整表。
最终实现预留151887个 MaybeUninit<isize> 值槽，与对照容量相同；这些未初始化槽不含预生成的初始邻居。不能据此声称总体内存下降。已写标记只在诊断/计数执行中维护，正式计时不更新它们。动态列表仍独立保存，保留原数组编号与有序内容。

【是否保持原标量 AMD】
是否提前合并：否，初始 Nv=1，J 标量编号及维度不变。
通过99/99组支持的输入/参数配置：3个真实案例，加96组稀疏/稠密、PQ/PV混合、控制参数配置。回退0，支持范围内跳过0，最终失败0。另4个不满足当前结构合同的输入被明确拒绝，不算新内核运行覆盖。
逐项比较所选主元/近似度数/组大小/已消元计数、有序消元前沿、变量列表更新/哈希/质量消元父节点、元素吸收、超变量合并、桶重新插入事件；记录结果一致。最终排列、逆排列、L估计和LU运算估计一致。后序处理的最终输出一致，中间每一步未单独记录。
首次排序不一致的位置：本次最终测试未发现。调试与release测试通过。

【性能】
同批 CPU0 P核、performance电源配置及EPP、release opt3、trace关闭、计数另跑。每组200次，2轮交替，预热每轮5次，共2400条记录。计时从入口开始，包括Ybus结构分析、准备、分配/清理、生成邻居、排序及后序；保留输出排列对象。复用仅复用输入元数据/动态存储；每次仍重新分析并重算排列，内核辅助向量仍按原实现分配。未测KLU factor/refactor或NR，本表不含它们。

【本阶段结论】
表示改变：已跑通并核查，没有完整初始邻居表。正确性：上述99组新路径实际运行并通过，无回退。性能：尚未加速，9241样本中位数首次分配慢2.16%，复用慢3.87%。本阶段没有把按需读取等同于性能提升。
读取次数没有下降：三个实际案例最终都访问了所有变量，9241生成112376个初始编号。因此当前仅消除了预先保存完整表，没有取得此前设想的首次过滤共享收益。下一件要验证的是：在这条真正按需读取路径上，共享同一PQ两变量首次触达时的过滤，是否能减少实际生成次数并抵消管理开销。尚未把该共享接入本路径。

## 代码与对照依据
基线仓库HEAD为1ad70a7a5834dd6d93c5c967115beb63e853f91b，实验改动未提交；具体源文件哈希见本批manifest与source-binary.sha256。当前系统AMD3.3.4/KLU2.3.6，long64；控制参数dense10/aggressive=true。原Rust标量核源于amd0.2.2，实际网络排列已与C参考核对；原源码作为对照保留。
上一阶段全展开入口 exact::order 在开始排序前为全部变量写arena，amd_2真正选点。当前计时对照 FullTableControl::order 使用同样全展开规则和原amd_2，支持复用缓冲，不创建未启用的首次共享辅助对象。旧结果的毫秒数不作跨批归因。
新入口 on_demand::Workspace::order / execute；初始邻居 InitialList::at；动态条目 NeighborStorage::write/read_dynamic；新实验内核 lazy_core::amd_lazy。旧amd_2.rs保留。没有调用旧核作为新路径回退。
位置范围上限采用可检查的n²逻辑地址上界，不据此分配n²内存；原内存压缩分支在新路径不得运行，所有实际测试计数为0并断言。

## 诊断中发现并修复的问题
提速过程中曾把所有列表读取都当成已写入动态列表。混合类型测试触发未初始化位置检查。第一个失败操作位于超变量比较：旧Rust移植在Len/Elen不等时仍继续扫描，并按较长列表长度读较短列表之后的存储。原C循环有ok &&条件，Rust源码留下TODO却未实现。新实验核改为长度不符就不读；旧参考核保留，逻辑状态和输出仍一致。操作级例子：同一哈希桶的列表[me,0,1]和[me,1]，长度已不等，继续按前者长度扫描后者会越界。修复后完整诊断和release回归通过；失败日志保留为on-demand-list-failure.log。
各轮中间实现只用于开发诊断：首轮每条读取检查存储位置、含计数；第二轮连续存储；后续区分初始/动态读取；最后正式批已关闭trace和计数。不同批绝对时间不混比。
